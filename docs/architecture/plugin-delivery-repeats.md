# Repeated plugin deliveries

> Code is the source of truth. This file is a map; when it and the code disagree, the code wins.

## Scope

A delivered slot's deposit that carries a `key`, and what Casa does when a plugin delivers a key
it already delivered: it sends nothing, and the call gets the original delivery's receipt. What a
delivered slot is, and how a link, a message and a proposal are posted and receipted, is
[`plugin-delivered-slots.md`](plugin-delivered-slots.md). Files are
[`plugin-delivered-files.md`](plugin-delivered-files.md); proposals and their keyboards are
[`stored-call-buttons.md`](stored-call-buttons.md).

## Mental model

**A plugin can name its post, so that a retry is the same post.** A plugin job posts a
message, then records that it posted it, in a second tool call. If Casa ends the batch between
the two, the next batch sees the post as unrecorded and posts it again. The plugin cannot close
that window itself: the post is an external write, and its record is a separate call. So the
deposit may carry the plugin's own identifier for the post (`key`). Casa remembers each key it
delivered, per installed plugin and operator. A later deposit with the same key is not sent;
the call's result is replaced by the original delivery's receipt, marked `repeat`. The plugin
records the delivery as usual.

**The memory is written at the instant a send is proven.** First the in-process map (which
cannot fail), then a private file (`/data/delivery_keys.json`). A failed write is logged and
never turns a proven delivery into a withheld one; the memory then lasts until a restart. Keys
are kept thirty days, and at most five hundred per plugin and operator.

## Contracts & invariants

**INV-PLUG-050**: A delivered slot's deposit may carry a `key` matching `^[A-Za-z0-9._:-]{1,128}$` (anything else is refused `bad_key` before a reference is minted); after a proven delivery of a keyed deposit the key is remembered for that plugin and operator, recorded synchronously at the point the send is proven; a later keyed deposit of the same kind whose key is remembered sends nothing and its result is replaced by the original delivery's receipt with `repeat` set — for a proposal only while the original keyboard is live, unclaimed, not past its deadline and registered under the same artifact as the new call, otherwise a fresh card is posted and remembered; deliveries of one key are serialised; a deposit without a key behaves as before.

A repeat still owes what is not the post: a file deposit's staged file is consumed, and a
`More` call's rewritten-input tell goes out as one labelled desk notice, because no card
carries it this time. Both await. A proposal's repeat is therefore decided again afterwards, with no await before
its receipt: one whose original was superseded, claimed or expired meanwhile is posted fresh,
without a second tell. A file's repeat keeps its first decision, since its staged copy is
already consumed. A card that brought pages (#1377) is one delivery: its receipt detail counts them, and its
repeat sends neither the pages nor the card. A repeat adds nothing to the post echo; the original is already
there, because a proposal's echo is filed at the instant its post is proven, before anything
else awaits.

What it does not cover: a send whose delivery was never proven (Telegram may have accepted
it before a timeout, as for any unproven send) is not remembered, so its retry posts again. A
plugin that reuses a key for different content gets the first content's receipt; keys are the
plugin's own identifiers. The memory is per installed plugin, so a reinstall under a different
runtime segment starts empty.

## Failure behavior

**The memory file is missing, unreadable or corrupt at boot.** Casa starts with an empty
memory: silently when the file is missing, with one warning when it cannot be read or parsed.
An entry is used only when it is exactly a shape Casa records (a delivered kind, that kind's
receipt detail and nothing else, a finite time, and for a proposal its registration, under a
well-formed plugin, operator and key); any other entry is dropped with one warning, and so is
one found unusable when it is looked up — the deposit is then delivered fresh. The expiry and
the per-plugin bound apply to what is read too. Boot never fails on it.

**The memory file cannot be written.** The delivery stands and its receipt is returned; one
warning is logged, and the key is remembered until a restart.

## Extension points

**Another delivered kind** joins the same memory: its proof point calls the same record step,
and its repeat says what it still owes when nothing is sent.
