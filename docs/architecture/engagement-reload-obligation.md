# Configuration commit reload

> Code is the source of truth. This file is a map; when it and the code disagree, the code wins.

## Scope

What a configuration commit reloads, and how: the path table that turns a commit's changed
paths into reload scopes, the shared helper the commit and the reload tools run a reload
through, and what the commit's reply says about a reload that failed. The reload scopes
themselves, their locks and the reload envelope's `failures` list are in
[`architecture/configuration.md`](configuration.md). The admission side of ending an
engagement is in [`architecture/engagement-completion-gate.md`](engagement-completion-gate.md);
completion owes no reload.

## Mental model

**A commit reloads what it changed, at once.** `config_git_commit` reads back the paths its
commit changed and runs the reloads the table names before it returns, so a change is live
when the commit is, two commits reload twice, and a task cancelled after a commit leaves that
commit live. Nothing waits for the end of an engagement, and nothing reads the caller's
engagement: the tool reloads the same way whoever calls it.

## Contracts & invariants

**INV-TOOL-014**: A non-empty `config_git_commit` runs, before it returns and whoever called it, the reloads `commit_reload_scopes` names for the paths the commit changed, each through the reload tool's fence and plugin-health refresh, and returns every reload's envelope; a reload that fails or reports failures leaves the commit standing and adds a warning.

The table is `reload.py::commit_reload_scopes`: a live resident's trigger inputs alone
(`triggers.yaml`, a `prompts/<trigger>.md`) reload its `triggers`, any other file of it its
`agent`; a resident or specialist that appears or goes, or a specialist's link (install,
upgrade, rollback, uninstall), `agents`; an edit inside a present specialist its `agent`;
`policies/` `policies`; an executor's definition `executors`. One kind runs as it is, once per
role; two kinds, a path the table does not know (`schema/`), or paths that could not be read
collapse to one `full`. A plugins-only commit reloads nothing — the plugin tools activate
their change and commit the registry themselves — and neither does a resident's staged
persona binding under `bindings/`, which only a restart activates (INV-CFG-003), nor an
executor's prompt, observer policy or doctrine, read when its next session starts. Each reload runs
through `tools.py::_run_reload`, the helper `casa_reload` and `casa_reload_triggers` use, so
the commit takes the plugin-tools fence exactly where they do (INV-CFG-011) and refreshes
plugin health after it.

What it does not cover: writes the repository does not track, which no commit can see — a
specialist's instance tuple, which `persona_apply` and the specialist bundle tools reload
themselves, and `plugin-env.conf`, whose `plugin_env` reload the configurator calls; commits
made without the tool — boot's re-bind commit, and the registry or trigger-file commits Casa
makes for its own writes — reload nothing through it; a
hand edit of the plugin registry stays inert until a `full` reload; and a failure the reload
treats as best effort and does not report is not seen. A resident whose staged persona awaits
its restart answers every reload of it with `restart_required`, so a `full` stops at that
resident until the restart.

## Failure behavior

**A reload fails, or reports failures.** The commit stays: nothing is rolled back. The reply
carries the reload's envelope beside the SHA and a warning that part of the change is not
live, which the configurator relays; a retry is its own `casa_reload`, or another commit.

**The commit's paths cannot be read.** The table reads an empty list as "reload everything"
and runs `full`.

**The table cannot be computed.** The commit logs it and runs `full`.

## Extension points

**A new reload scope** reaches a commit only through a row of `commit_reload_scopes`; a path
no row knows reloads `full`, so a scope without a row costs a wider reload, never a missing
one.
